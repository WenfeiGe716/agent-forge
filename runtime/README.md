# Agent Forge runtime adapters

This directory contains the OpenCodex provider gateway. The current product
backend and team runtime live in `rust/`; Electron and the default launchers use
`forge-server`. Codex owns native model/tool execution. See
[team validation](../docs/VALIDATION_TEAM_RUNTIME.md) for the current tools,
skills, messaging and callback path.

The Python bridge and POC notes below describe retained migration tooling;
they are not the default product execution path.

## Codex

`backend/forge/runtime_bridge.py` launches the project-built top-level `codex`
binary, never the globally installed CLI. Each client owns an independent
`CODEX_HOME`, OS user home, XDG directories and file-based credential store.
The initialize response must confirm the requested runtime home. Ambient
credentials are removed; explicit route credentials use `FORGE_*` names.

The bridge preserves upstream Thread/Turn/Item IDs and request IDs. It supports
streaming notifications, server-request responses, interrupt, same-thread
resume/steer and paginated history. `RuntimeEventRecorder` projects each
normalized event into the existing Forge `Event` table, so the normal
`/api/runs/{run_id}/events` and SSE stream can replay the same ordered records.
It does not make approval decisions and is not yet a multi-agent task scheduler.

Stage 1 adds `forge.codex_task.CodexSingleTask` as an explicit single-task POC.
It writes a key-free Responses provider config for one isolated runtime, passes
the secret through `FORGE_MODEL_KEY`, starts one independent Thread, and
returns ordered streaming events. Use `scripts/verify-codex-task.py` for a real
upstream check; `FORGE_POC_BASE_URL`, `FORGE_POC_MODEL`, and
`FORGE_POC_API_KEY` must be supplied explicitly. The POC does not read app
configuration or auto-select a provider. Its `approval_policy=never` is only
for no-side-effect validation and is not the production permission policy.

桌面原型可在显式设置 `FORGE_CODEX_POC=true` 后调用
`POST /api/runtime/poc-task`。请求只提交已保存的 `provider_id`、
`model_profile_id` 和任务文本；服务端读取加密密钥，响应为不可缓存的 NDJSON
事件流。该入口只允许开发者/管理员，使用独立运行目录，不创建或改写旧的
Forge Run，也不会把失败自动改成新任务。提供 `run_id` 时可把 POC 的事件
持久化到已有 Run；默认关闭。

阶段 1 另外提供默认关闭的
`POST /api/runs/{run_id}/codex-start`。它只读取该 Run 冻结的负责人主模型和供应商凭据，
把 Codex 事件写回同一个 Run，并在完成、暂停或异常时更新 Run 终态；不会创建替代任务。
开启前仍需完成正式权限映射、取消/恢复和真实工具验收。

## 清理旧运行数据

`scripts/cleanup-runtime.py` 默认只做 dry-run，列出将清理的运行记录和目录。
只有显式传入 `--delete` 才会删除 Run/Task/Event（保留全局事件）、消息、审批、
会议和运行工作副本；Provider、模型、Agent、Skill、项目与布局配置不受影响。
执行前必须先检查 dry-run 输出；个人 `~/.codex`、`~/.opencodex` 和符号链接路径
会被拒绝。

## OpenCodex

`opencodex-gateway.ts` uses the prepared source's programmatic server API.
Never replace it with `ocx start`, `setup`, `sync`, `shim` or service commands.

- Prepare with `bash scripts/prepare-opencodex-gateway.sh`.
- The original submodule remains unchanged. A separate build copy applies the
  reviewed loopback-token patch under `patches/opencodex/`.
- The launcher checks the upstream commit and patch digest, full upstream
  config schema, explicit port, hub role, disabled native integrations and
  disabled built-in account forwarding. Provider routes come from Forge, not
  the operator's personal account/configuration.
- Native ownership/resolution callbacks prevent personal service-state
  inspection. Upstream labels these callbacks test-only: they are a
  version-pinned adaptation, not an upstream stability guarantee.
- A Forge-scoped data-plane token is mandatory. The upstream's unmodified
  loopback mode ignores tokens; the build patch makes an explicitly configured
  token mandatory on loopback too. Never remove it without equivalent protection.

These internal settings are to be generated by Forge's configuration layer;
they are not additional everyday settings for end users.

## Checks

Run backend bridge tests, `bun test runtime/opencodex-gateway.test.ts`, and the
two `scripts/verify-*-runtime.py` / `verify-opencodex-gateway.py` smoke tests.
The gateway smoke test is macOS-specific and additionally denies access to
personal runtime directories at the OS level. Smoke tests exercise real
processes and protocols but send no model request. A real model/tool/task
acceptance run remains a separate requirement before migration.

`python scripts/verify-opencodex-codex-route.py` exercises the complete local
protocol chain with a disposable upstream HTTP server: real Codex binary,
real pinned OpenCodex gateway, distinct gateway/upstream credentials,
namespaced model routing, and `/v1/responses` forwarding. It deliberately
sends no request outside the temporary local process tree.

## Forge gateway admission configuration

For a saved Responses provider routed through the Forge gateway, configure the
backend with `FORGE_OPENCODEX_GATEWAY_URL` set to its complete inference base URL
(for example `http://127.0.0.1:10100/v1`) and
`FORGE_OPENCODEX_API_AUTH_TOKEN` set to the same private token used by the gateway
process. Keep the saved model selector in `provider/model` form. The gateway must
already have that provider and its upstream credential configured.

The scheduler's leader and member sessions, the POC, and the formal start endpoint
resolve this token separately from the saved provider credential. Matching includes
scheme, hostname, port and path; other provider URLs keep their direct auth. A
matching route without a valid token fails before starting Codex. These settings
do not launch the gateway, synchronize its providers, or package it for desktop.
