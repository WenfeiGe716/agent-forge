# 架构与状态契约

## 请求与执行路径

浏览器 → Nginx → FastAPI → PostgreSQL中的运行/配置快照与Outbox → Temporal → Python Worker → 模型服务或独立沙箱broker → gVisor代码容器。

业务成果写入本地文件区，结构化事件写入数据库。办公室、任务图、详情和执行时间线读取同一个运行数据与事件流。前端不通过播放动画推进业务状态。

## 核心实体

- Provider/ProviderRevision：可停用的连接和不可变凭据版本。
- ModelProfile/Agent：模型与角色配置，带版本号。
- Project：访问成员、项目规范、验收命令、导入基线。
- Run：任务输入、配置快照、状态、调用统计、计划/成果摘要。
- Task：工作区、角色、依赖、执行消息、结果与集成基准。
- Step：执行前占位和完成结果，用于识别完成/未确认状态。
- Outbox：持久化的启动、控制和审批请求。
- Event：单调ID、类型、时间、run_id和结构化数据。

接口细节见 `openapi.json` 或运行中的 `/api/docs`。当前使用SQLAlchemy建表，没有引入正式数据库迁移工具，升级前需要迁移方案。

## 执行状态

`queued → planning → awaiting_approval → running → verifying → reviewing → awaiting_acceptance → completed`。

测试或审查失败可进入 `reworking` 再回验证；超过上限转 `needs_attention`。用户拒绝计划转 `cancelled`；拒绝成果转 `needs_attention`。暂停显示 `paused`，恢复回原阶段。审批操作绑定 `plan_digest/artifact_digest`，不允许用旧审批批准另一份内容。

API只记录控制意图，不把“已请求暂停”冒充“已经暂停”。正在进行的模型请求/沙箱命令结束或超时后，编排器在安全边界应用控制。本版不能保证即刻取消所有在途外部操作。取消保留工作区，不改原项目。

## 协作规则

负责人只读规划，计划是带负责人、依赖与验收要求的DAG。开发/测试角色能修改工作区和执行命令，审查角色只读。每个并行任务从当前集成基线复制工作副本；任务完成后依次应用patch。不能干净集成的冲突保存补丁并转人工，不用“最后写入覆盖”冒充成功。

依赖完成后，下游任务获得集成代码和结构化交接摘要。独立审查读取最终集成副本和真实测试报告。不同Agent可以选择不同供应商，但不会共享长期密钥或完整跨项目历史。

## 可靠性边界

工作流只写编排逻辑，模型/文件/网络IO全部在Activity。Activity默认不盲目自动重试；执行前写Step记录，已完成可返回缓存结果，已开始但没确认完成则保留现场并转人工。Temporal历史持久化可以恢复编排，但不解决任意外部操作的恰好一次语义。

Outbox按创建顺序投递，同一运行的前置消息失败时不越过投递后续消息；工作流以command_id去重。启动请求用固定workflow_id。沙箱操作使用参数摘要与不可重复的operation_id；结果不明时返回不确定状态，不重复执行。

这种第一版策略偏保守：Worker中途崩溃可能需要人工处置，而不是完全自主从任何中间点恢复。手动重试创建新Run，不能把回放、恢复和重执行混为一谈。

## 可视化

SSE使用事件ID，支持Last-Event-ID断线补发；初始快照由API提供，界面定期轮询校正。撤销账号/项目访问后停止事件访问。办公室最多显示12个角色并基于真实任务点亮状态；更多角色仍可在列表/任务图查看。第一版不包含完整走路/开会动画、任意办公室编辑器、任意历史时刻的3D回放或时间轴拖动。

当前3D模块采用程序化低多边形几何体，无外部人物资产。WebGL失败时看板与日志仍可使用。
