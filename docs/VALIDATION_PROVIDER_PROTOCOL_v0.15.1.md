# v0.15.1 供应商协议与模型参数修正

## 原因与范围

2026-09-10 的桌面报错「适配器尚未实现参数: max_tokens」由旧模型配置与新连接协议不兼容导致：供应商由 Chat Completions 改为 Responses，但既有模型的参数声明和值未随之改变，保存供应商时又缺少兼容性检查。批量启用复用参数校验，因此一条旧配置阻止整个批次进入确认。

网页原配置能复现相同问题，不是桌面迁移引入。前端批量操作只提交配置 ID、版本和目标状态，不生成 max_tokens。

本次仅在用户当前桌面工作空间修正「bailian/glm-5.2 · 联调模型」（配置 ID `51379c32d1314ed1ab3d1a01cf9ab566`）：

- 参数声明：`max_tokens` → `max_output_tokens`。
- 参数值：仍为 4096。
- 通过实际桌面编辑表单保存，配置 v1 → v2；原版本和 model.updated 审计保留。
- 其他模型、供应商连接及修订、Agent、已有运行的组合 SHA-256 在修改前后相同。
- 原网页工作空间未修改，不做两端自动同步。

## 更新时发现并修复的启动竞态

实际 .app 在启动页尚在加载时再次 loadURL 相同 boot.html，会在特定时序下使第二次加载也报 `(-3)`，后台尚未启动即进入错误提示。真实 Electron 44 读取原 app.asar，在 10/20 ms 间隔下复现；请求白名单均允许该文件，资源存在，与用户截图一致。导航事件契约同时参考 [Electron webContents 文档](https://www.electronjs.org/docs/latest/api/web-contents#event-will-frame-navigate)，没有通过放宽导航策略处理。

修复为等待首次页面加载并复用已完成的启动页，保留真实资源加载失败的错误处理。打包后再次运行真实 Electron 回放，0/1/2/5/10/20/50 ms 及显式串行的 8 种时序全部通过：后台均启动一次，无 ERR_ABORTED。

最终 .app 已在真实桌面打开工作台，原 8 位成员及组织布局 v2 可见。检测到用户继续操作后停止界面自动操作。更新没有重建工作空间或更改钥匙串。
