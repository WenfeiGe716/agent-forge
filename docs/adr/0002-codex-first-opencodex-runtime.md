# 使用 Codex 作为执行运行时、OpenCodex 作为多供应商网关

Agent Forge 当前同时维护固定流程、模型调用、本地工具、审批、重试和活动状态，造成任务失败后无法在原任务内恢复、实时输出不可靠、供应商能力判断不准确等问题。我们决定将 Codex App Server 作为真实执行运行时，将 OpenCodex 作为本地多供应商协议与模型路由网关，Agent Forge 保留团队、成员、任务、权限、审批治理、工作区和 3D 展示；三者之间只通过 Runtime Bridge 交换版本化任务和运行事件。两个上游都以项目内固定源码版本构建，绝不读写用户现有的 `~/.codex` 或个人运行配置。

## 考虑过的方案

- **继续扩展现有 Forge 执行器**：短期改动少，但会继续重复实现模型循环、工具协议、审批和恢复，不接受。
- **深度 fork Codex 并把团队逻辑写进 fork**：执行能力强，但升级成本和合并冲突会把团队业务绑定到上游内部实现，不接受。
- **只使用 OpenCodex，不接 Codex App Server**：能解决供应商差异，不能解决本地执行、审批、流式事件、恢复和工具生命周期，不完整。

## 后果

正面结果是执行语义、流式事件、工具和审批有明确的事实来源；负责人可以在同一个 Task 中继续、重试和转派；供应商适配与组织治理解耦。代价是需要管理两个上游版本、两个本地进程和一层桥接契约，并且必须接受部分 App Server 接口仍可能发生变化。通过锁定版本、生成并保存 schema、建立兼容性矩阵、真实供应商验收和可回滚的 sidecar 发布来控制风险。

Codex 源码按 Apache-2.0 保留许可证与修改声明；OpenCodex 按其 MIT 许可证保留声明，并在产品中明确它是独立社区项目，不代表供应商或上游服务方。

运行时使用 Agent Forge 自己的数据目录作为 `CODEX_HOME`，并清除继承的 Codex 配置、会话和插件路径。这样可以在使用上游源码的同时，不改变用户本机已经安装的 Codex 客户端行为。

源码检查后的必要约束：Codex 子进程还必须使用独立的用户/XDG 目录，并强制文件凭据存储，避免隐式导入个人 Skill 或钥匙串。OpenCodex 仅调用专用网关入口，禁用客户端同步与服务归属检查。原始 submodule 保持不变；对上游默认跳过 loopback 鉴权的行为，使用可审查的独立构建补丁。构建记录上游 commit 与补丁摘要，升级时必须重新通过鉴权与隔离测试，不能静默丢弃补丁。
